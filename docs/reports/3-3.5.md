# Task 3.5 — Observability and the orphan reaper

**Role:** `backend-core` · **Wave:** 3 · **Date:** 2026-09-18
**Defects addressed:** D-58 (health/readiness, DELETE semantics, docs gating), D-20 (orphan reaper)

## What was built

### Health and readiness (D-58)

`GET /api/health` is unchanged: an unconditional liveness literal that touches nothing. New
`GET /api/health/ready` checks the two dependencies the process actually needs — a real
`SELECT 1` against `DB_PATH`, and that `PDFS_DIR` exists and is writable — and answers 503 with
per-check detail (`{"status": "unavailable", "checks": {"database": {"ok": false, "detail":
"..."}, ...}}`) if either fails. D-58's motivating case, "a container with a corrupt database
reports itself healthy," is now caught: a corrupt SQLite file opens without error and fails on the
first real statement, which is exactly what the readiness check runs.

### DELETE semantics (D-58)

Read D-58 as "three routes return 204, two return 200" and it sounds like inconsistency to fix.
Read the five routes and the split was already correct: `DELETE /api/master-resume`,
`DELETE /api/resumes/{id}` and `DELETE /api/chat` remove a resource outright (204, nothing left to
describe); `DELETE /api/rules` and `DELETE /api/system-prompt` reset a singleton row to its seeded
default (200 with the resulting resource, because the row still exists with a new value). No
endpoint's path, verb or status code changed. What was missing was the convention being *stated*
rather than accidental — each of the five routes now says which kind it is in its own docstring,
and `docs/adr/0007-delete-verb-status-code-convention.md` records the rule so a future `DELETE`
route follows it on purpose.

### `/docs`, `/redoc`, `/openapi.json` (D-58)

New `Settings.API_DOCS_ENABLED: bool = True`. When true (default, current behaviour), nothing
changes. When false, `create_app` passes `docs_url=None, redoc_url=None, openapi_url=None` to the
`FastAPI()` constructor, which removes all three routes from `app.routes` entirely.

Before gating anything, checked whether task 2.2's `npm run api:generate` depends on the served
`/openapi.json` — it does not. `api:export` runs `python -m resumetailor.api.openapi <path>`
(`api/openapi.py::main`), which imports the application object directly and calls
`render_openapi(app)`; it never makes an HTTP request. Gating has zero effect on the export
pipeline in either direction. See `docs/adr/0006-docs-gated-by-setting.md`.

### Metrics

New `core/metrics.py`, built on `prometheus-client` (**a new dependency — see "Deviations and
decisions that need sign-off" below**):

- `resumetailor_http_requests_total` / `resumetailor_http_request_duration_seconds`, recorded once
  in `RequestContextMiddleware` so no router needed to change for this half. Labelled by the
  *route template* (`scope["route"].path`, e.g. `/api/resumes/{resume_id}`), not the raw path, to
  keep cardinality bounded; an unmatched path (a 404) labels as `"unmatched"`.
- `resumetailor_sse_streams_active`, a side effect of `SSEStreamTracker` (see Graceful shutdown).
- `resumetailor_reaper_runs_total{trigger}`, `resumetailor_reaper_rows_relinked_total`,
  `resumetailor_reaper_files_deleted_total`, `resumetailor_reaper_rows_missing_pdf` (a gauge, not a
  counter — it is "as of the last run," not cumulative).

Served at `GET /api/metrics` (`api/routers/metrics.py`), same trust boundary as every other route
today (no auth model yet; D4/B-03 open).

### Graceful shutdown

`core/metrics.SSEStreamTracker` counts in-flight SSE streams. `resumes.py::generate_resume_stream`,
`chat.py::chat_stream` and `evaluate.py::evaluate_stream` each wrap the whole body of their
`event_gen()` in `async with sse_stream_tracker.track():`. `main.py`'s `lifespan`, after `yield`,
waits up to `Settings.GRACEFUL_SHUTDOWN_TIMEOUT_S` (default 60s) for the count to reach zero before
returning — returning is what lets uvicorn close the remaining connections, so without the wait a
generation mid-stream would be cut off the instant shutdown began. A timeout logs a warning rather
than blocking indefinitely.

**This is the application-level half only.** Task 3.4's Dockerfile does not yet pass uvicorn a
matching `--timeout-graceful-shutdown`, so on `docker stop`, the container's own shutdown window
(uvicorn's default is short) can still be shorter than the 60s this code will wait for. Flagged in
`PLAN.md`'s change log for whoever lands 3.4; not filed as a blocker because it does not block this
task's own completion, and `Dockerfile*` is not a file this task owns.

**A real bug found and fixed along the way:** the tracker's first implementation used
`asyncio.Event`. An `Event`'s internal future binds to whichever event loop first calls `.wait()`
while the event is unset, and stays bound for the object's life. In production that is harmless —
one process, one event loop, for the whole run — but the test suite runs a fresh event loop per
test while reusing the module-level `sse_stream_tracker` singleton, so the second test to exercise
a non-empty tracker raised `RuntimeError: <Event ...> is bound to a different event loop`. Rewrote
`wait_drained` as a bounded poll loop (50ms interval) instead, which has no loop affinity at all.
Caught by `tests/test_main.py`'s own graceful-shutdown tests, not by inspection — worth naming
because it is the kind of bug that would have looked fine in a manual `curl` check and broken the
first time CI happened to schedule two SSE-adjacent tests back to back.

### Orphan reaper (D-20)

`store_tailored_resume` (`domain/tailoring.py`, owned by `backend-domain`) writes a row, then a
PDF file, then updates the row — no transaction across the two. Its own docstring names the gap and
says fixing it is this task's job, "not here." `core/reaper.py::reap_orphans` reconciles the state
from outside that function, using only the repository calls it already uses
(`list_resumes`, `update_resume`), paging past `list_resumes`'s `MAX_PAGE_SIZE` so every row is
checked, not just the first page:

- A row with `pdf_path IS NULL` whose `<PDFS_DIR>/<id>.pdf` already exists is **relinked**
  (`update_resume(..., pdf_path=...)`) — the crash was between the file write and the row update,
  and relinking is the exact statement the crashed request was one step away from making. No data
  lost.
- A row with `pdf_path IS NULL` and no matching file is **left alone**, only counted
  (`resumetailor_reaper_rows_missing_pdf`). Its `yaml_content` is intact — `create_resume` writes
  it before the PDF step — and `POST /api/resumes/{id}/render` already re-renders any row
  regardless of `pdf_path`. Deleting this row would discard real content to "fix" a gap the
  application already recovers from through its existing render endpoint.
- A PDF file matching no row at all — the only unambiguous garbage — is deleted.

This is a deliberate deviation from a literal reading of D-20's own docstring, which frames the
second case as "a file on disk that no row references" (implying deletion). Relinking when possible
and leaving-with-visibility otherwise is strictly better: it never discards content a user could
recover, and it still cleans up the one case that is unambiguously garbage. Recorded here per
AGENTS.md §10 as a judgment call, not silently.

Runs once at startup, before the process accepts requests (so a previous crash's mess is never
visible to the first request this boot serves), and then every `Settings.REAPER_INTERVAL_S`
(default 1h) as a background `asyncio.Task`, cancelled and awaited on shutdown.

## Deviations and decisions that need sign-off

- **New dependency: `prometheus-client`.** AGENTS.md §10 lists "a dependency needs to be added
  that is not already in the plan" as an explicit stop-and-ask trigger. The task brief that
  assigned 3.5 pre-authorized dependency *selection* for the metrics surface ("check what's
  already available... don't add a heavy new dependency for a small surface") but did not name a
  library, so this is not treated as silently pre-cleared — it is recorded as decision **D11** in
  `PLAN.md` §5 for explicit sign-off. Chosen for being pure Python, zero transitive dependencies,
  and no server of its own (`GET /api/metrics` calls `generate_latest()` and returns text from this
  process's own ASGI stack). If rejected, the fallback is a hand-rolled counter/gauge dict behind
  the same route; `core/metrics.py` is the only file that would need to change.
- **D-20's reaper recovers rather than only deletes** (see above) — a deliberate improvement over
  the literal defect description, not an oversight.
- **Task 3.4 cross-reference**, not a blocker: the Docker-level half of graceful shutdown
  (`--timeout-graceful-shutdown` on the uvicorn CMD) belongs to task 3.4's `Dockerfile`, which this
  task does not own and which had not landed as of this work. Noted in `PLAN.md`'s change log.
