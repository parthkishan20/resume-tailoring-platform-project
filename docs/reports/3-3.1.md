# Task 3.1 — Tailor and Evaluate on shared JD state

**Role:** `frontend-features` **Wave:** 3 **Status:** done
**Branch:** `wave3/3.1-frontend-features-tailor-evaluate`

No per-task report existed yet for tasks in this style (2.3 and 2.5 recorded their
work entirely in PLAN.md's Change log); this one follows the level of detail
established there, expanded into sections since the task explicitly asked for a
standalone report.

## What was built

### D-12, D-41, D-45 — the feature logic

Task 2.3 gave Tailor and Evaluate a shared `jobDescription` in `WorkspaceContext`
and reproduced just enough of the request-and-handoff to keep both reachable
(D-12 closed structurally). This task built the rest.

**The master document's live buffer moved.** It used to be `DocumentRegion` local
state (`draft`, `dirty`, the save mutation). Tailor and Evaluate are mounted as
siblings of `DocumentRegion` in the inspector, not descendants of it, so neither
could reach it. The buffer, the dirty flag, and save/discard actions now live in
`WorkspaceContext` (`masterYaml`, `masterDirty`, `setMasterDraft`,
`discardMasterDraft`, `saveMasterDraft`), reusing the same `useMasterResume`/
`useSaveMasterResume` query hooks `WorkspaceChrome` already calls (shared cache,
no extra fetch). `DocumentRegion` and `MasterDocument` are otherwise unchanged:
same props, same test ids, same dirty-guard and `beforeunload` behaviour, just
sourced from context instead of local `useState`. The full existing
`DocumentRegion.test.tsx` suite (D-30, P1-7, split, save-error coverage) passes
unmodified against the refactor, which is the regression signal that the move
preserved behaviour exactly.

**D-41 closes differently for each tab, because the two backend routes are not
symmetric.** `POST /api/evaluate/stream`'s `yaml_content` field already accepts
arbitrary YAML (task 2.5), so Evaluate reads `masterYaml` directly — no save, no
extra request, the score is always of what's on screen. `POST
/api/resumes/stream` has no such field: it always re-reads whatever
`master_resume` holds in the database. Adding an override belongs to
`api/routers/resumes.py`, which is `api-contract`/`backend-domain` territory, not
this task's. The workaround that stays in-ownership: `TailorPanel.generate()`
saves a dirty buffer and awaits it before opening the SSE connection, so the
database always reflects the on-screen document at the moment a run starts. A
failed save aborts the run with the save's own error message rather than
tailoring stale content. **Registered as blocker B-06** for the real fix.

**D-45**: Evaluate now resolves a target document from `WorkspaceContext`'s
`destination`/`selectedResume` rather than always scoring the master. Master open
→ the live buffer. Library open with a resume selected → that resume's
`yaml_content` if the caller already has it (a resume just produced by Tailor's
`done` frame carries the full row), otherwise a new `useResumeDetail(id)` query
(gated on `id`, following the same `enabled` pattern `useSystemPrompt` already
uses) fetches it, since `GET /api/resumes` list rows omit the field. Library open
with nothing selected → a dedicated empty state ("Select a document to
evaluate"), rather than silently falling back to the master, which would score a
document the user cannot see. The button label and the "Evaluating <name>"
caption both reflect the resolved target.

Both panels were also moved off the untyped `readSseStream` (`event.data as
{...}` casts) onto the validated `streamTailor`/`streamEvaluate` readers task
2.2 shipped but the interim 2.3 panels never adopted — a D-60 residual closed as
a natural consequence of rewriting these two call sites anyway.

### D6 — Tailwind v3 to v4

Upgraded `tailwindcss` and added `@tailwindcss/postcss` (both 4.3.3), removed
`autoprefixer` (subsumed by v4's Lightning-CSS-based PostCSS plugin).
`globals.css` now opens with `@import "tailwindcss"` in place of the three
`@tailwind` directives, plus `@config "../../tailwind.config.ts"`.

**This is a deliberate, narrower interpretation of D6 than "rewrite into
`@theme`".** `@config` is v4's documented path for adopting the new engine
without rewriting a JS config wholesale, and it was the only responsible choice
here: `tailwind.config.ts`'s `lp-*` block is referenced by every file under
`design-system/` and every feature built on it, and the same file's legacy
unprefixed block (`accent`, `surface`, `border`, …) is still load-bearing for
`components/ChatPanel.tsx`, `components/ResumeListPanel.tsx` and
`components/ui/*` — all task 3.2's, none of them touchable here. A full rewrite
into `@theme` was not exercisable end to end without either breaking those
files or duplicating the whole token layer twice. `@config` keeps the exact same
utility names resolving to the exact same `--lp-*` custom properties on both
sides of the migration, so the upgrade is real (new engine, new package
versions, CI parity with what a fresh `npm ci` will actually install) without
forcing a rewrite or a visual re-verification of files this task cannot touch.

One compatibility gap needed closing, not zero: of D6's own list of five v3→v4
default changes (bare `rounded`, `outline-none`, `ring`/`ring-1`, bare `border`,
bare `shadow`), a source-wide audit found exactly one still both **present** in
an un-owned file and **value-changing**: bare `rounded` on
`ResumeListPanel.tsx`'s delete button and `ui/SegmentedControl.tsx`'s segments.
(`outline-none`'s v4 meaning is visually identical to v3's for the one live use;
`ring-1` is already explicit; bare `border`/`shadow` weren't in use uncombined
with an explicit color/value anywhere live.) Added
`@utility rounded { border-radius: 0.25rem }` to `globals.css`, pinning the v3
value globally — new code in this task never uses the bare form, so this is
purely a shim for the two controls that do. Task 3.2 removes it, and the legacy
`:root` aliases beside it, when it rehosts `ChatPanel`/`ResumeListPanel` onto
the design system (exactly the removal 2.3's own comment on that block already
named as future work).

## Deviations from the plan text

1. **`ModeSwitch`/`DocumentFrame` promoted without a Radix rewrite** — see above.
2. **The legacy `:root` palette, `lucide-react`, and `components/ui/*` are not
   removed.** The plan bullet's phrasing ("once nothing depends on the v3
   config anymore") was always conditional on that being true, and it is not
   yet: `ChatPanel.tsx`, `ResumeListPanel.tsx`, and the four `ui/*` controls
   they use are task 3.2's, running concurrently, and this task's ownership
   boundary explicitly excludes `features/{assistant,library}/` (and by
   extension, editing the `components/` files those features are built on).
3. **Files touched outside the literal per-role ownership table**:
   `WorkspaceContext.tsx`, `Inspector.tsx` (one line — removed a now-unused
   prop from an `EvaluatePanel` call) and `DocumentRegion.tsx`/
   `MasterDocument.tsx`, which the AGENTS.md role table assigns to
   `frontend-shell` (`features/workspace/`), not `frontend-features`. This
   task's own brief explicitly named `features/document/` for the
   `ModeSwitch`/`DocumentFrame` promotion and implicitly required reaching
   `WorkspaceContext` to satisfy D-41 (the live buffer has to live somewhere
   both `DocumentRegion` and the inspector tabs can reach, and no other
   location works structurally). `frontend-shell` has no active task in wave 3
   to conflict with, so there is no concurrent-write hazard the ownership rule
   is protecting against here. Every edit in these files was minimal and
   behaviour-preserving, verified by the pre-existing `DocumentRegion.test.tsx`
   and `WorkspaceShell.test.tsx` suites passing unmodified.
