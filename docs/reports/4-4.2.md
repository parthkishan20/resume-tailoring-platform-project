## D-76 and D-77: demonstrated, and D-76 turned out to be a bigger bug than reported

Both are `test.fail()`-pinned in `09-accessibility.spec.ts`: the suite stays green today
(Playwright reports an expected failure as a pass), and goes red — for the right reason —
the moment someone actually fixes the underlying component without removing the
annotation, which is the signal a maintainer needs to know the pin can come out.

**D-76.** Task 4.1's report framed this as "the dialog's own Confirm/submit action gets
swallowed once it's open." Building a keyboard-only reproduction here found something more
fundamental: **the dialog never opens via keyboard at all.** Focusing the row's
`rename-resume` icon button and pressing Enter never produces a `rename-input` element
(`element(s) not found`, confirmed via a direct `--reporter=json` capture of the failure,
not inferred); the same is true of `delete-resume` and `[role="alertdialog"]`. The
mechanism: `ResumeListRow`'s `onKeyDown` is attached to the *row*, so it also catches the
Enter keydown bubbling up from any focused *descendant* — including the row's own action
buttons — before that button's native Enter-triggers-click default action can fire. It
calls `preventDefault()` unconditionally (suppressing the click Radix's trigger needs) and
also fires the row's own `onSelect()` (meant for the row, not its buttons). A mouse click
bypasses this entirely, which is exactly why 06-library.spec.ts's mouse-driven flows have
always passed.

A closely related finding, folded into D-76 rather than given a new number: axe's
`nested-interactive` rule fires on `ResumeListRow` too — it renders `role="button"` on
itself while nesting two real `<button>` elements inside. This is arguably the root
architectural issue the keydown collision sits on top of, so it's recorded alongside D-76
in PLAN.md rather than separately.

**D-77.** Demonstrated two ways: a bounded (5s) click-timeout test at the suite's real
default viewport (1280×720, not the 1600×900 several other Library specs use to route
around this exact bug), and a real screenshot baseline,
`library-document-header-overlap-d77.png`, which visibly shows "Re-render" overlapping
"Tailor" and "Delete" overlapping "Evaluate" — legible garbage in the rendered page, not a
subtle pixel diff.

## New defects found while building this suite

**D-87 (P1).** The YAML editor's CodeMirror instance does not follow dark mode at all —
its own background stays white regardless of theme, while the syntax-highlight text colors
correctly do switch to their dark-appropriate values. Confirmed precisely, not just
observed: `getComputedStyle` on `.cm-editor` in dark mode reports `--lp-paper-raised`
correctly resolving to `#1e1e23` right there, but the element's actual painted
`background-color` is `rgb(255, 255, 255)` regardless. The CSS variable is available and
correct; the theme's own background rule is not winning. `.cm-editor` carries several
CodeMirror-generated theme hash classes simultaneously, consistent with a stale or
duplicate theme compartment left behind by `@uiw/react-codemirror`'s reconfigure on theme
change — not diagnosed further, since `editorTheme.ts`/`YamlEditor.tsx` are not `qa-e2e`'s
files. The result is not a borderline contrast miss: axe measured 45-95 serious
`color-contrast` violations on this one element tree, every time, on every dark-mode
surface that mounts the editor. See `master-document-editor-dark.png` for what this looks
like rendered — near-white text on a white background is barely legible.

**D-88 (P2).** Two structural gaps in the same editor, independent of theme: (a)
`aria-input-field-name` — `.cm-content` (the actual `contenteditable` text input) has no
accessible name reaching it, even though `YamlEditor.tsx` passes `aria-label={label}` to
the `<CodeMirror>` wrapper; the prop lands on the outer wrapper, not the inner element a
screen reader lands on. (b) `scrollable-region-focusable` — `.cm-scroller` renders
`tabindex="-1"`, so the editor's own scrollable viewport has no keyboard path to focus and
scroll independent of editing. The same rule (b) also fires, independently, on an unrelated
component: onboarding's sample-YAML preview (`OnboardingRoute.tsx`'s `<pre
className="...overflow-auto...">`) has no `tabindex` either. Folded into D-88 rather than
given its own number, since it's the same rule and the same fix shape.

**PLAN.md task 1.4's own recorded `--lp-ink-tertiary` AA gap** ("ships darker than the
spec value in both themes; the spec's own value fails the AA that its section 7 requires")
is now a live-reproducible test (4.49:1 measured against 4.5:1 required) instead of only
prose — confirmation, not a new finding.

## One finding not pinned, and why

Evaluate's dashed empty-state box (before anything is evaluated) measured 3.9:1 against a
4.5:1 requirement on one run, then passed clean on a rerun — genuinely flaky across
repeated executions, unlike the two AA-boundary findings above (4.42-4.49 vs 4.5, close
enough that sub-pixel/rounding variance across runs is a believable explanation on its
own). A 3.9:1 miss is not a rounding-distance failure, so the flakiness itself is the
finding here: this is either a real, intermittent design-token or render-timing issue, or
an artifact of this specific test methodology, and it was not possible to tell which within
this task's time. Per the task brief's own guidance, this was excluded from the gate scans
(a documented exclusion in `09-accessibility.spec.ts`, not a silent drop) rather than forced
into a `test.fail()` pin that would itself be unreliable. Worth a closer look by whoever
next touches `EvaluatePanel.tsx`'s empty state or `--lp-ink-secondary`.

## Decisions

- **New devDependency `@axe-core/playwright@^4.10.2`**, added to `test/package.json` only.
  Recorded as PLAN.md decision D12 per this task's brief (a judgment call on an
  already-owned, well-known, zero-risk devDependency, not an escalation).
- Axe's `include`/`exclude` context selectors are independent selectors, not a shadow-DOM/
  iframe selector chain — passing more than one to a single `AxeBuilder.exclude()`/
  `.include()` call is silently misinterpreted as "find B inside A." `helpers.ts`'s
  `scanForBlockingViolations` calls `.include()`/`.exclude()` once per selector to avoid
  this; worth knowing before extending this suite.
- Three components' own known/tracked issues (`[data-testid=yaml-editor]` /
  `[data-testid=resume-yaml-editor]` for D-87/D-88, `[data-testid=resume-list-item]` for
  D-76's nested-interactive finding, `.text-lp-ink-tertiary` for the task-1.4 AA gap, plus
  two flaky/borderline exclusions noted above) are excluded from the general "surface" axe
  scans and covered instead by their own precisely-scoped, `test.fail()`-pinned tests. This
  keeps the general scans meaningful (a real, new regression on any of those pages will
  still fail them) rather than permanently red for reasons already on file.
