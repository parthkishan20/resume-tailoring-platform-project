# Task 4.1 — QA: rebuild the e2e suite

**Role:** `qa-e2e` **Wave:** 4 **Date:** 2026-09-18

## Summary

The eight e2e specs in `test/e2e/` were written against the four-destination icon-rail UI task
2.3 replaced with the three-zone workspace, and task 3.1/3.2 replaced the interim panels again
with the real Tailor/Evaluate/Library/Assistant surfaces. All eight were stale — selectors,
flows, and the nav itself no longer exist. They are replaced by eight new specs covering the
current product, closing D-27 and D-29. A real Docker daemon was reachable this task (as it was

read against source. That live run found four real product bugs, all now in the defect register,
none of which any amount of static reading would have caught.

## Real bugs found, only reachable by running the thing

### D-73 (P0) — the e2e stack's own container could not boot

`docker-compose.test.yml`'s `tmpfs: [/app/db, /app/pdfs]` entries carry no `mode`/`uid`/`gid`.
The file's own comment claims "a tmpfs mount is created mode 1777 (the kernel's default for tmpfs
with no `mode=` option)" — true of a bare Linux `mount -t tmpfs`, but not of what this Docker
Compose version (v5.1.3, Docker Desktop) actually does with a short-form `tmpfs:` list entry:
confirmed directly (`docker run --tmpfs /app/db resumetailor-e2e:latest stat -c '%a %U:%G'
/app/db` → `755 root:root`). The app's non-root `uid 10001` (from D-72/task 3.4's own hardening)
cannot write into a `755 root:root` directory, so `sqlite3.connect` fails with `unable to open
database file` at the same `migrate()` call site D-72 broke, before the healthcheck can ever pass
— `playwright`'s `depends_on: condition: service_healthy` then never starts.

Confirmed the fix by running the container with an explicit mode (`docker run --tmpfs
/app/db:mode=1777,uid=10001,gid=10001 ...`): boots clean, migrates, serves `/api/health`. Not
fixed in `docker-compose.test.yml` itself — that file is `platform`'s, not `qa-e2e`'s. Logged in
the defect register with the exact fix (`tmpfs: - /app/db:uid=10001,gid=10001,mode=1770`, or
equivalent long-form `mode:`/`uid:`).

### D-74 (P0) — every mock-generated resume's stored YAML is invalid

While seeding data for `06-library.spec.ts`'s edit test, `PATCH /api/resumes/{id}` with the
*unmodified* freshly-generated content 422'd: `"cv.phone: This is not a valid phone number."` —
but the actual stored document, fetched directly, turned out to contain far more than a bad phone
number. `GET /api/resumes/{id}` on a resume the mock backend just generated returns something
shaped like:

```yaml
cv:
  name: Mock User
  ... (a complete, otherwise-valid generated CV) ...

Master:
cv:
  name: Mock User
  ... (the entire master resume, duplicated) ...

JD:
Gamma Corp — Engineer
```

Traced to `backend/src/resumetailor/llm/stub.py`'s `SimulatedBackendAPI.complete`, the
`"ResumeAuditor" in system` branch:

```python
start = user_content.find("cv:")
return user_content[start:] if start != -1 else MOCK_GENERATION_RESULT_YAML
```

The real audit prompt template puts the candidate CV first, then appends a `Master:` section (for
the auditor's context) and a `JD:` section after it. `find("cv:")` correctly locates the
candidate's own start, but `user_content[start:]` returns everything from there to the *end of the
whole prompt* — including the trailing sections the stub was never meant to echo back.

This is invisible everywhere except a strict-validated write against already-stored content:
`PUT /api/master-resume` and `POST /api/resumes/stream` both write through the lenient
`normalize_to_rendercv` path (which prunes, not rejects), and the mock PDF renderer ignores its
YAML argument entirely and returns a fixed fixture PDF, so a rendered preview looks fine
regardless of what's actually stored. Nothing before this task tried a strict-validated write
against a mock-generated resume's *stored* content: `PATCH /api/resumes/{id}` with `yaml_content`,
or the assistant's `edit_master_resume` tool. Confirmed the tool half too, in isolation: sending
"edit my master resume" to the deterministic chat stub always returns the same phone-number
validation failure as its tool result and never completes an `AssistantAction` — the tool-call
path for `edit_master_resume` is unconditionally, deterministically broken under `LLM_MOCK`.

Not fixed here — `llm/stub.py` is `llm`'s file. Logged with the exact branch and what it needs to
stop at (the candidate CV's own extent, not the rest of the prompt).

**Worked around in the suite**, not hidden: the YAML-edit test in `06-library.spec.ts` seeds a
known-valid document via `PATCH` before driving the UI (mirroring how `setMasterResume` already
seeds the master resume via the API rather than depending on a UI-driven creation path), and
`07-assistant.spec.ts`'s tool-call test uses the `update_generation_rules` trigger instead of
`edit_master_resume`, with a comment explaining why.

### D-75 (P2) — the fixture phone number itself fails validation

Independent of D-74: `MOCK_GENERATION_RESULT_YAML`'s phone number, `"+10000000000"`, fails
`phonenumbers.is_valid_number` (confirmed directly in the running container: `False`, versus
`True` for `"+14155552671"`). `sample-resume.yaml` and `MOCK_IMPORT_YAML` carry the same number.
Worked around by using a corrected phone number only where the suite performs a strict-validated
write, via a `.replace()` on the loaded fixture rather than editing `test/fixtures/sample-resume.yaml`
in place. `test/fixtures/` is this task's to own, but `sample-resume.yaml` is deliberately
byte-identical to `llm/stub.py`'s `MOCK_GENERATION_RESULT_YAML` (also shared with
`backend/tests/helpers/llm_stub.py`), and editing one without the other would break that intended
parity rather than fix the underlying number. Logged for whoever next touches `llm/stub.py` to
change both together.

### D-76 (P2) — a real keyboard-accessibility bug, found trying to drive dialogs by keyboard

The first version of `confirmAlertDialog` drove Radix's `AlertDialog` by keyboard: Tab from its
documented initial focus on Cancel, then Enter on the resulting focus (Confirm). This worked for
the master-resume delete dialog and failed, silently, for the Library's per-row delete and rename
dialogs — "silently" meaning the row stayed on screen with no error, so the *count* assertion
timed out with no clue why. Traced with request-logging: the keyboard path issued no
`DELETE`/`PATCH` call at all.

Root cause: `ResumeListRow` (`features/library/ResumeList.tsx`) puts `onKeyDown` directly on the
`data-testid=resume-list-item` row, unconditionally calling `event.preventDefault()` on Enter or
Space (its own select-on-Enter behaviour). Radix's dialog content is portalled to
`document.body`, but stays a React *child* of whatever opened it — and React's synthetic events
bubble through the component tree, not the DOM tree. So Enter pressed on a button inside a dialog
opened from within that row bubbles into the row's handler before the dialog's own control ever
acts on it. A mouse click does not go through `onKeyDown` at all and is unaffected — which is how
this was actually diagnosed (comparing the working master-resume case, whose delete button is not
nested in any row, against the failing per-row case).

This is a real product bug, not just a test inconvenience: any keyboard-only user trying to
confirm a rename or delete from a Library row cannot. Logged in the defect register with the exact
fix (`event.target === event.currentTarget`, or `stopPropagation` from the portalled dialogs).
Not fixed here — `ResumeList.tsx` is `frontend-features`'s file. The suite's
`confirmAlertDialog`/`submitRenameDialog` now click the actual button instead (`confirmAlertDialog`
clicks the last button inside `[role="alertdialog"]`; `submitRenameDialog` clicks
`[role="dialog"] button[type="submit"]`), which is unaffected by this bug and also sidesteps B-08.

### D-77 (P2) — a layout bug, found as a `locator.click` timeout

`06-library.spec.ts`'s "deleting the open document from its header" test hung for the full 60s
test timeout retrying a click on `delete-resume-document`, reporting `<button role="tab" ...
Evaluate> intercepts pointer events`. Screenshot confirmed it: at the suite's default 1280×720
viewport, with the nav expanded (216px), the Library list column (320px, fixed) and the Inspector
(380px, default width) all present, `GeneratedResumeDocument`'s own column is left only ~364px —
and its header commits to a single row at the *global* `lg` breakpoint (1024px viewport width)
regardless of that column's actual width, so its five actions (rename, Save, Re-render, Delete,
plus the mode switch) visually overlap the Inspector's tab strip and become unclickable.
`MasterDocument`'s own header comment already flags needing "about 390px" for four fewer controls
of the same kind; `GeneratedResumeDocument` added a fifth (Re-render) without revisiting that
math. Not reproduced on `MasterDocument`'s header, and not reproduced at a wider viewport.

Not fixed here — `GeneratedResumeDocument.tsx` is `frontend-features`'s file. Worked around by
widening the viewport for the one `describe` block this affects (`06-library.spec.ts`'s "Library:
document" block, `test.use({ viewport: { width: 1600, height: 900 } })`), with a comment
explaining why, rather than force-clicking through a broken layout or silently dropping coverage
of these flows.

## Blocker: B-08 — `AlertDialogContent` has no `data-testid` on its actions

`design-system/AlertDialog.tsx`'s `AlertDialogContent` renders Confirm and Cancel with no
`data-testid`, so no destructive-confirmation flow in the product (delete master resume, delete a
generated resume, delete a Library row, clear the chat) can be driven by testid alone. Worked
around with a structural locator (`[role="alertdialog"] button` — last, since Confirm always
renders after Cancel), not a text or position-in-a-list selector, but still not the convention
AGENTS.md §9 asks for. Logged as B-08 with the exact fix (optional `confirmTestId`/`cancelTestId`
props threaded to `RadixAlertDialog.Action`/`.Cancel`, and the four call sites that would need to
pass one). Flagged specifically for task 4.2, which will want this for its own accessibility
assertions.
