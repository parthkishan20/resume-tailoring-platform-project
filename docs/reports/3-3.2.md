# Task 3.2 — Library and Assistant

**Role:** `frontend-features`
**Branch:** `wave3/3.2-frontend-features-library-assistant`

## What was built

### Library (D-45)

`frontend/src/features/library/` now has a list beside a document, the same
shape the centre region uses everywhere else:

- `ResumeList.tsx` — the list column. Sort (`ResumeSortControl.tsx`, date /
  job description, ascending / descending), pagination (`ResumePagination.tsx`,
  driving the `page` param `useResumeList` already accepted but nothing ever
  set), rename and delete per row.
- `GeneratedResumeDocument.tsx` — the document for whatever row is selected.
  Editor / Split / Preview over the resume's YAML, reusing
  `features/document/{ModeSwitch,YamlEditor,DocumentFrame}.tsx` rather than
  duplicating them (the same pieces `MasterDocument` uses), Save (`PATCH`),
  Re-render (`POST .../render`, deliberately a separate action from Save
  because `PATCH` validates and stores YAML but does not render, D-04), Delete,
  Download, and rename from the header.
- `RenameResumeDialog.tsx` — shared by the list row and the open document.
- `LibraryDocument.tsx` — rewritten from a wrapper around the legacy
  `components/ResumeListPanel.tsx` into the real composition of the two pieces
  above, still owning the selection/open/clear wiring into `WorkspaceContext`
  that task 2.3 built.

`ResumeSortControl.tsx` is a small local radiogroup rather than a `Select` or
`SegmentedControl`: neither is in `design-system/` yet (PLAN.md's 3.1 bullet:
"`Select` was never needed by 2.3 and is untouched"), and this follows the
same precedent `features/document/ModeSwitch.tsx` set for the identical gap.
Promoting either belongs with whichever task adds
`@radix-ui/react-select`/`@radix-ui/react-toggle-group` to the design system.

### Assistant (D-33's UI half, D-21)

`frontend/src/features/assistant/Chat.tsx` replaces the re-hosted
`components/ChatPanel.tsx` task 2.3 kept in place as a pass-through:

- The typed `streamChat` reader from `@/lib/api` instead of a cast
  `readSseStream` call.
- The full DESIGN-SYSTEM.md §4.3 state matrix for Assistant: empty
  (suggested first messages), loading (skeleton lines), error (inline alert
  with retry, and a per-turn retry for a failed send), streaming (token by
  token), success.
- A generic seam for task 3.3's tool-calling work, running concurrently: when
  a `done` frame's `result.action` is non-null, the UI describes it by
  humanizing `action.type` (`master_resume_updated` → "Master resume
  updated") rather than hard-coding 3.3's eventual four type strings, and
  invalidates `queryKeys.masterResume` (always) and `queryKeys.resumes.all`
  (when `action.resume_id` is set) through the same `QueryClient` every other
  surface reads from. At the time this shipped, 3.3 had not landed a tool
  call, so `action` is always `null` in the running app; the seam is exercised
  by `Chat.test.tsx`'s fabricated-action test.
- Chat pagination, half closed — see below.

`AssistantPanel.tsx` keeps its clear-conversation `AlertDialog` and now
mounts `Chat` instead of the legacy panel.

## D-21: chat pagination, why it is only half done

The task brief anticipated this and named the conflict-protocol path to take
if the backend route needed a change this task does not own. It does.

`GET /api/chat` (`backend/src/resumetailor/api/routers/chat.py`) declares no
query parameters at all in task 2.2's exported OpenAPI contract — confirmed
by reading `frontend/src/lib/api/generated/openapi.json`'s `/api/chat` `get`
operation directly, not assumed. It always returns the full transcript,
oldest first. `backend/src/resumetailor/api/` is `backend-core`'s, not this
task's.

What shipped instead is the frontend-only half: `Chat.tsx` renders the most
recent 30 of whatever `useChatHistory` fetched, with "Load earlier messages"
revealing more from the array already in memory. That bounds the DOM, not the
network payload — the thing D-21 actually names as the cost ("`GET
/api/chat` returns every message ever").

The repository layer already has what a real fix needs and is not using it:
`get_chat_messages(db_path, user_id, limit)` in
`backend/src/resumetailor/db/repositories/chat.py` returns the most recent
`limit` messages today (used internally by `chat.py`'s own LLM-context call),
but the route's own `GET` handler passes no `limit` and exposes none. Logged
as **B-06** in PLAN.md §6 with the exact files and the two owners it needs:
`backend-core` for the query parameter on the route, `data` for a `before_id`
cursor in the repository if true backward paging (rather than "most recent
N") is wanted.

## Deviations from the plan bullet

- **`components/ChatPanel.tsx` and `components/ResumeListPanel.tsx` are now
  dead code, left in place.** Both are unreferenced by the app after this
  change (verified: `grep` finds no import outside their own standalone
  tests and this report's prose). Deleting them, and their tests under
  `frontend/src/__tests__/`, touches files outside this task's owned paths
  (`frontend/src/components/`, `frontend/src/__tests__/`). Flagged in
  PLAN.md's 3.2 bullet for the same follow-up cleanup pass task 3.1 is doing
  for the panels it supersedes, rather than done here.
- **No changes were needed to `frontend/src/features/document/__tests__/DocumentRegion.test.tsx`
  or `frontend/src/features/workspace/__tests__/WorkspaceShell.test.tsx`**,
  both outside this task's owned paths and both written against the
  placeholder `ResumeListPanel`/`ChatPanel`. They still pass unmodified: the
  new components carry the same `data-testid="resume-list"` and
  `data-testid="chat-panel"` container testids the placeholders did, and
  `useChatHistory`'s `?? []` guard (see its doc comment in `queries.ts`)
  keeps a test double that stops at `jest.fn()` with no resolved value from
  tripping TanStack Query v5's "query data cannot be undefined" error, which
  only ever surfaced because the Assistant tab is `forceMount`ed and so
  renders for real in every shell-level test now, not just the ones that
  mean to exercise it.
- **Rename is a dialog, not inline editing.** `design-system/Input`'s
  contract always renders a visible label above the field (no
  placeholder-as-label, no hidden-label escape hatch), which reads oddly
  inline in a list row or a document header, so `RenameResumeDialog.tsx` uses
  `Dialog`/`Input` with a normal visible "Resume name" label instead.
