## Ranked findings

### D-73 (P1, Security) — Tool-calling has no per-round cap on the number of tool calls

**File:** `backend/src/resumetailor/domain/assistant.py:513-538` (`run_assistant_turn`)

`run_assistant_turn` bounds the conversation to `MAX_TOOL_ITERATIONS = 4` **rounds**, and the round
after the budget is spent is asked with no `tools` at all — that half is genuinely provably bounded,
exactly as its own docstring claims. What is not bounded is **how many tool calls one round may
contain**: `for call in tool_calls: outcome = await _execute_tool(...)` executes every tool call the
model returns in a single response, with no cap on `len(tool_calls)`.

**Concrete failure scenario:** a single POST to `/api/chat/stream` — one token spent against task
2.4's rate limiter, which was calibrated on "one request to a provider-calling route costs one or two
provider calls" — can cause the model to emit, say, ten `generate_tailored_resume` calls in one round.
Each one runs `domain.tailoring.tailor()` (two more provider calls: the generate pass and the audit
pass) and a real `rendercv` subprocess invocation. Across up to four rounds, the fan-out compounds:
one rate-limited request can legitimately trigger dozens of provider calls and render invocations,
which is exactly the cost/resource-exhaustion outcome task 2.4's limiter exists to prevent (D-28's
cost half). The render subprocess's own semaphore and per-call timeouts keep any single fan-out from
being unbounded in *time*, but not in *count*, and the token bucket sees it as one request.

This is reachable two ways: an unusually chatty or misconfigured provider response, or a genuine
prompt-injection payload (a job description or an imported PDF's extracted text, both of which flow
into model context) that asks the model to "call generate_tailored_resume for each of these ten
variations." The four-tool fixed action set (D8/ADR 0005) already bounds *what* can be done; this
bounds *how many times per turn*, which nothing currently does.

No test asserts a bound on `tool_calls` per round — `test_domain_assistant.py` only exercises the
round cap (`MAX_TOOL_ITERATIONS`), never a round returning more than one call.

**Recommendation (for `backend-domain`, which owns `domain/assistant.py`):** cap `len(tool_calls)`
per round (a small constant, e.g. 1-3, matching what a legitimate single-turn request should ever
need) and treat any excess as a tool-result explaining the limit, the same pattern `_execute_tool`
already uses for every other kind of tool-call failure.

### D-74 (P2, Security) — `/api/health/ready` returns raw driver exception text and filesystem paths

**File:** `backend/src/resumetailor/api/routers/health.py:37-52` (`_check_database`,
`_check_pdfs_dir`)

`_check_database` puts `str(exc)` — a raw `sqlite3.Error` message — directly into
`CheckResult.detail` on failure, and `_check_pdfs_dir` puts an f-string containing the absolute
`PDFS_DIR` path into the same field. Both reach the client verbatim: `/api/health/ready` is
unauthenticated and always reachable (it is in `middleware.py`'s `_QUIET_PATHS`, i.e. expected to be
polled routinely, by design).

**Concrete failure scenario:** a corrupt or locked database (D-58's own motivating case) yields
something like `unable to open database file: /app/db/resumedb.db` or `database is locked` in a
200/503 JSON body any caller can request with no auth. This is the same category of disclosure D-53
treats as P1 everywhere else in the application ("raw provider/subprocess exception text reaching the
client") — narrower here (a short driver string and a path, not a full traceback), but not opaque,
and inconsistent with the opacity `client_message`/`.detail` split every other error path in this
codebase now enforces. `api/schemas/health.py`'s own docstring calls this "never sensitive, since it
is about a filesystem path or a SQLite error" — I disagree with that framing on the margin: the path
confirms the container's internal layout to an unauthenticated caller, which is exactly the kind of
detail D-53's rationale says should stay server-side.

Given D4's loopback-only posture this is low urgency today, but it is new surface, unreviewed until
now, and the inconsistency is worth closing on the same terms D-53 already set for the rest of the
API.

**Recommendation (for `backend-core`, which owns `api/routers/health.py`):** classify the failure
(e.g. `"database unreachable"`, `"pdfs_dir not writable"`) instead of interpolating `str(exc)` or a
path into `detail`; log the real exception server-side with the request id, the same split every
other error path in this application already uses.

### D-75 (P3, Ops) — Independent re-assessment of D-71: real risk is lower than "13 vulnerabilities" suggests

**Files:** `frontend/next.config.js:1-7`, `Dockerfile` (no Node runtime in the final stage — only
`frontend-builder`'s `out/` directory is copied into `python:3.12-slim`), `npm audit --json`

D-71 is accurate about what `npm audit` reports (confirmed independently — 24 advisories against
`next`, 1 critical, several high, all requiring a Next 16 major bump to clear) but its framing
understates one fact that changes the practical risk: **this application never runs a Next.js server
in production.** `next.config.js` sets `output: 'export'`; the Dockerfile's Python runtime stage
copies only the static `out/` directory and has no Node.js installed at all. The large majority of
the advisories `npm audit` lists — Server Actions SSRF and DoS, Middleware bypass and cache
poisoning, the Image Optimization API RCE and DoS pair, RSC cache confusion, the Windows RCE via path
traversal — are all vulnerabilities in Next's *server* runtime (middleware, Server Actions, the
Image Optimizer, the RSC cache), none of which exist as a running process here. A grep of
`frontend/src` for `next/image`, `next/script`, `next/server`, and `middleware.ts` returns nothing, so
even the client-side XSS advisories (`beforeInteractive` scripts, CSP-nonce handling) have no code
path in this app that could trigger them.

This does not mean D-71 should be closed — staying on Next 14 has real costs (no security backports,
eventual forced migration, support lifecycle) — but the *security* urgency of the Next 16 upgrade is
close to zero for this specific deployment shape, not "mitigated somewhat" as D-71's current text
says. I recommend the orchestrator append this context to D-71's own entry (outside this task's
ownership to edit directly) so a future pass does not over-prioritize a breaking major-version bump on
security grounds when the actual residual risk here is near-nil; the upgrade is worth doing on its own
schedule for DX and support reasons.

**One more thing found while re-running the audit, separate from the reachability argument above:**
a fresh `npm ci` + `npm audit` today reports **74** vulnerabilities (2 moderate, 71 high, 1 critical),
not the 13 D-71 recorded from task 3.4's run the same day. The lockfile has not changed — nobody has
touched `frontend/package-lock.json` since 3.4 — so the growth is `npm audit`'s advisory database
itself being live and updated continuously, not new advisories in the dependency tree. The new
findings include one **outside** the `next` family: `nanoid` (pulled in transitively through
`postcss` → `@tailwindcss/postcss`, i.e. the Tailwind v4 build tooling tasks 3.1/3.4 added), "No fix
available," non-secure ID generation under a negative or zero `size` argument. Same conclusion as
above by the same method: it is a **build-time** dependency invoked internally by PostCSS with
hardcoded arguments, never with attacker-controlled input, so it has no reachable exploitation path
in this application either — but it is worth naming because it demonstrates the actual operational
gap: `ci.yml`'s `audit` job is intentionally non-blocking for `npm audit` (correctly, per D-71's own
reasoning), which means a number this volatile can grow 5-6x between two runs on the same day with
nothing but a GitHub Actions `::warning::` annotation to notice it, and nobody is looking at that
annotation's *trend*, only whether the job is green. Worth a line in D-71 (or a follow-up task) noting
that "reporting only" should include watching the count over time, not just running the command.

## Regressions checked, all confirmed clean (task 2.4's original scope, spot-checked against every
wave-3 change)

- **Rate limiting.** `RATE_LIMITED_PATHS` (`core/security.py`) still names exactly the four
  provider-calling routes, and none of tasks 2.5/3.1-3.6 added a fifth provider-calling route outside
  it — `/api/chat/stream`'s tool-calling upgrade (3.3) reuses the same route and is covered by the
  existing limit (see D-73 above for the residual gap: it counts requests, not the LLM/render calls
  a request can now fan out into).
- **Input bounds (D-47/D-69).** All five original D-47 fields and `ResumeUpdate` (D-69, closed by
  2.2) are still `Field(max_length=...)`-bounded; `domain/assistant.py`'s own tool-argument models
  (`_EditMasterResumeArgs`, `_GenerateTailoredResumeArgs`, `_EvaluateResumeArgs`, `_RuleArg`) reuse the
  same constants task 2.4 defined, so the new tool-calling surface inherited the bound rather than
  reopening it. **D-70 (`RuleItem`/`RulesBody`, `PUT /api/rules`) is confirmed still open** — no task
  since it was registered has bounded it; this is not a regression, it was already known and already
  registered, and `api/routers/rules.py` is not a file this task can write.
- **Non-root container.** `Dockerfile` still creates and switches to `USER app` (uid 10001) before
  any `rendercv` child can run; task 3.4's full Dockerfile rewrite (D-65, D-51, D-72) preserved this
  exactly.
- **CORS.** No `CORSMiddleware` was added anywhere in the diff; the documented non-decision in
  `core/security.py` still holds and nothing in wave 3 introduced a second origin.
- **Opaque client errors (D-53).** `chat.py`, `resumes.py`, and `evaluate.py` all still frame
  `exc.client_message`, never `str(exc)`, in every SSE error branch, including task 3.3's rewrite of
  `chat.py` — confirmed by reading the merged file, not just the change log's claim.
  `domain/assistant.py::_execute_tool` extends the same pattern to tool failures (`exc.client_message`
  fed back to the model, never `str(exc)`), which is the right pattern given a tool failure is now a
  third opaque-error surface alongside HTTP and SSE.
- **Path traversal (D-25).** `resolve_within()` is still the only way `resumes.py` joins a stored
  `pdf_path` to `PDFS_DIR`, at both call sites (`get_pdf`, `delete_generated`).
- **Subprocess env scrub (D-49) / render sandboxing (D-50).** `subprocess_env()`'s allowlist and the
  Dockerfile's `tmpfs: /tmp` mount are both unchanged by any wave-3 task.
- **Dependency scan wiring (D-63/D-71).** Independently re-ran `pip-audit` (clean; the only skip is
  the project's own unpublished package, expected) and confirmed `ci.yml`'s `audit` job is genuinely
  blocking: `pip-audit` runs with no `|| true`, and the aggregate `ci` job fails if `audit` fails.
  `npm audit`'s failure is explicitly swallowed with `|| echo "::warning..."`, matching D-71's
  "reporting only" claim. Confirmed `aiohttp==3.14.3` and `anyio==4.15.1` in `backend/uv.lock` (both
  CVE fixes from task 3.4 actually landed) and `next@14.2.35` in `frontend/package.json` /
  `package-lock.json`.
- **Secrets.** Ran `gitleaks dir . --redact` (working tree) and `gitleaks git . --redact` (full
  history, 89 commits) independently with the same pinned `v8.30.1` binary CI uses. Both clean.
  `planning/master-resume.yaml` and both `.env` paths checked and confirmed still gitignored.

## Other surface reviewed, no finding

- **`Settings.API_DOCS_ENABLED` (D9).** Still defaults `true`. Given every route in this API is
  already unauthenticated and undocumented-vs-documented makes no difference to what an unauthenticated
  caller can already do (the whole surface is readable from source), leaving `/docs` on by default is
  still the right call for a single-user, loopback-only deployment. No change recommended; revisit
  together with D4 as already planned.
- **`/api/metrics` (task 3.5).** Confirmed it exposes only counts, durations, and route *templates*
  (never raw paths or resume ids — `RequestContextMiddleware` labels by `scope["route"].path`), so
  there is no per-resource cardinality or content leak. Consistent with the loopback-only posture;
  no finding.
- **SQL injection.** Grepped every repository module for string-built queries; the one dynamic
  `UPDATE` (`db/repositories/resumes.py::update_resume`) builds its `SET` clause from a fixed set of
  hardcoded column-name fragments chosen in Python, never from caller input, and every value is still
  bound as a parameter. No injection surface.
- **YAML deserialization.** Every YAML parse in the backend (`resume_schema/normalize.py`,
  `resume_schema/validate.py`, `rendering/config.py`) uses `yaml.safe_load`, never `yaml.load` or an
  unsafe loader. No change since 2.4; confirmed still true across every wave-3 addition.
- **PDF extraction (`pdf/extract.py`, `pymupdf`).** Bounded to 10 MB / 50 pages before parsing;
  `pymupdf==1.28.0` (current, `pip-audit` clean); the raw MuPDF exception text is wrapped in
  `PDFExtractError`, whose `client_message` is a fixed string — `str(exc)` never reaches the client,
  consistent with D-53's pattern.
- **Assistant tool-argument validation.** Every tool handler in `domain/assistant.py` validates its
  arguments through a Pydantic model before doing anything (`_EditMasterResumeArgs` et al.), and
  `edit_master_resume` independently calls `resume_schema.validate` before writing — closing D-04 for
  the assistant path specifically, even though `PUT /api/master-resume` (the manual save route) still
  does not validate (D-04 stays open there, unowned by this task). Malformed JSON, an unknown tool
  name, and a `ValidationError` are all caught in `_execute_tool` and turned into a tool-result
  sentence rather than an exception that could unwind the stream or reach the client raw.
  `RATE_LIMITED_PATHS` and `resolve_within` are the only two `core/security.py` primitives the
  assistant tools do not themselves need (they never touch a file path or the rate-limited routes
  directly), and neither omission is a gap.
- **Stored system prompt as a prompt-injection primitive (D-28).** Already registered and already
  P0. Worth stating plainly given this task's brief: task 3.3 makes this materially worse in kind, not
  just in principle — before 3.3, an attacker who could rewrite the stored system prompt (D-28's
  existing no-auth path) could only steer the assistant's *text*; after 3.3, the same primitive can
  steer real tool execution (overwrite the master resume, spend provider credits generating resumes,
  change generation rules). This does not change D-28's severity (already P0, already the top
  finding in the whole register) but it is the concrete reason D4/B-03 (the auth model) should stay
  the first thing revisited before any deployment beyond loopback, now more than before 3.3 shipped.
