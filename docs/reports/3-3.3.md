# Task 3.3 — Assistant tool calling (D-33)

**Role:** `backend-domain`  **Wave:** 3  **Date:** 2026-09-18

## What shipped

The chat assistant can now perform four real workstation actions instead of
being a plain streaming completion with `"action": null` hardcoded. This is
D-33, PLAN.md's single largest product gap, one of the three stated core
product principles, and closed the way decision D8 / ADR 0005 already scoped
it before this task started: a **fixed four-tool set**, not a generic "hand
the model the API surface" design.

## The tool taxonomy

| Tool | Effect | Write path |
|---|---|---|
| `edit_master_resume` | Replace the master resume with a complete new YAML document | `resume_schema.validate` (refuses a non-rendering document), then `upsert_master_resume` |
| `generate_tailored_resume` | Tailor the master resume to a job description, render it, store it | `domain.tailoring.tailor` + `store_tailored_resume` — the same pipeline `POST /api/resumes/stream` runs |
| `evaluate_resume` | Score the master resume, or a specified generated one, against a job description | `domain.evaluation.evaluate` — the same call `POST /api/evaluate/stream` runs |
| `update_generation_rules` | Set the listed `(section, rule_key)` rules, leaving every other rule alone | `upsert_rules` |

**Deliberately not exposed**, per ADR 0005:

- **No delete tool of any kind** — not the master resume, not a generated
  resume, not chat history. Deletion stays a deliberate human action.
- **No system-prompt tool.** A model rewriting the prompt that governs its
  own future turns is a self-modifying loop with no upside here, and the
  system prompt is already a documented prompt-injection surface (D-28).
- **No generic API access, no raw path, no SQL.** Every tool's arguments are
  a small, explicit JSON Schema; there is no "call this endpoint" escape
  hatch.

Each tool's arguments are model-authored text turned into JSON, so they are
validated exactly as an HTTP request body would be — bounded string lengths
reusing `core/security.py`'s `MAX_*_CHARS` constants where a tool's field
matches an existing one, and a fresh `Field(max_length=...)` where it does
not (the rule list, since `RuleItem` in `api/routers/rules.py` is D-70,
itself still unbounded in a file this task does not own — bounding the
*tool's* copy independently keeps a model-authored rule list from becoming a
way around a limit the equivalent HTTP route still lacks).

## Why D-04 needed independent handling here

ADR 0005 names the hazard directly: "every tool call must go through the
same validated write path as the UI, not a shortcut... which matters because
`PUT /api/master-resume` does not validate today." That gap (D-04) is still
open on the manual save route — `api/routers/master_resume.py` is not owned
by this task, and task 2.5 (which closed D-04 on `PATCH /api/resumes/{id}`)
explicitly left it, since that file wasn't its file either. Going through
"the same path" the UI uses would therefore have *inherited* an open P0
defect into a new, LLM-reachable surface. `edit_master_resume` closes it
independently: it calls `resume_schema.validate` and refuses a document that
will not render, before writing, exactly as `PATCH /api/resumes/{id}`
already does. The manual `PUT` route's own gap is unchanged and remains
tracked under D-04.

## Design points

**The LLM port gained tool calling.** Task 2.1 built the streaming lifecycle
(timeouts, retry, the empty-content guard, usage accounting) and deliberately
left `tools` unwired — closing it was named as this task's job. `llm/port.py`
adds `ToolSpec` (name, description, JSON Schema parameters), `ToolCall` (id,
name, raw argument JSON), and `StreamEvent = str | ToolCall`.
`LiteLLMAdapter.stream()` takes an optional `tools` sequence, translates each
to the OpenAI-compatible `{"type": "function", "function": {...}}` shape, and
accumulates a tool call across however many chunks the provider fragments it
into — `id` and `name` arrive once, `arguments` slices the way a text delta
does. A tool call is yielded only once fully assembled, after the stream
ends: unlike text, half a tool call is not actionable, so there is nothing to
gain from yielding it early and a real hazard (a caller trying to parse
partial JSON) in doing so.

**The stub gained deterministic tool-call simulation.** `llm/stub.py`'s
`SimulatedBackendAPI` is what both the pytest suite and `LLM_MOCK=true` (the
e2e stack) run against, so it needed the same capability with no network and
no real model judgment involved. A small trigger table
(`MOCK_TOOL_TRIGGERS`) maps a fixed phrase in the latest user message to one
tool and one canned argument set, mirroring the existing pattern
(`MOCK_GENERATION_PROGRESS`, `classify()`/`respond()` in
`tests/helpers/llm_stub.py`) of routing by input shape rather than by
judgment. Once the working conversation already carries a `role: "tool"`
message — meaning a call from an earlier round in the same turn already ran
— the stub answers in plain text instead of triggering again, which is what
lets a scripted two-round test terminate deterministically and mirrors the
fixed four-tool set's "no runaway tool loop" intent.

**The orchestration lives in `domain/assistant.py`, not the route.**
`run_assistant_turn` is an async generator with the same shape
`domain.tailoring.tailor` already established: yield events as they happen
(`str` for a text delta), then exactly one final event
(`AssistantReply(text, action)`). It streams the model, and if the model
asked for one or more tools, executes each (sequentially, against the real
domain services and repository functions — not reimplemented), appends the
assistant's tool-call turn and each tool's result to a working copy of the
conversation, and asks again. This repeats for at most `MAX_TOOL_ITERATIONS`
(4) rounds of tool calls; the round after the budget is spent is asked with
no `tools` argument at all, and — this is the one design point worth calling
out — **that round's result is treated as final unconditionally**, not
because a well-behaved provider cannot return a tool call it was never
offered (it cannot), but because the loop should not have to trust that
guarantee to be provably bounded. `api/routers/chat.py` (touched by
necessity: D-33 cannot close without a `done.result.action` change, and no
other wave-3 task owns this file per AGENTS.md §2) is a thin adapter over
this generator, exactly the split task 2.5 drew between `domain/tailoring.py`
and its route.

**Tool-call round trips are not persisted.** Only the final user message and
the final assistant text reach `chat_messages` — the same two `INSERT`s the
route always did. A tool call and its result are working state for one
request's LLM context, not something `GET /api/chat` should ever surface.

**Errors reuse D-53's opacity pattern instead of reinventing it.** A failed
tool call — invalid arguments, a domain error from the tool's own work (a
render failure, a provider outage), an unknown tool name, malformed JSON
arguments — never raises past `_execute_tool`. It becomes a `client_message`
-safe sentence fed back to the model as the tool's result, so the model can
explain the failure in its own words and the turn continues rather than the
SSE stream ending in an `error` frame. The operator-facing detail is still
logged, at `exc.code`, the same as every other domain-error path in this
codebase.

## What is deliberately not built

**No `event: progress` narration for a tool-invoked generation's three
internal stages.** `POST /api/resumes/stream` narrates
analyzing/tailoring/rendering as separate SSE frames; a chat-invoked
`generate_tailored_resume` does not — there is one "the assistant is
working" gap on the client (already covered by the existing chat UI's
"Thinking…" state) rather than three narrated stages. Extending
`STREAM_CONTRACTS` and `frontend/src/lib/api/sse.ts`'s `ChatFrame` for one
nested case inside a tool call was judged not worth widening a contract this
task would only be touching by necessity; the chat SSE vocabulary stays
exactly `token` / `done` / `error`, unchanged, which also means this task
touches zero frontend files and zero generated API-contract artifacts.

**No system-prompt-driven tool discovery.** The four tools' descriptions
(handed to the provider in the function schema) are the only thing telling
the model what it can do and when. The stored system prompt is
user-editable content and a documented prompt-injection surface (D-28), so
it deliberately carries none of the tool vocabulary.

- New test files: `backend/tests/test_llm_tool_calls.py` (adapter-level:
  fragment assembly, multiple simultaneous tool calls, text-then-tool-call,
  the "not yielded until complete" guarantee, the provider schema
  translation), `backend/tests/test_domain_assistant.py` (domain-level, no
  HTTP: all four tools' success and failure paths, D-04 closure on
  `edit_master_resume`, D-53's opacity on a render failure, the round-budget
  termination guarantee, malformed/unknown tool calls), plus additions to
  `backend/tests/test_llm.py` (the stub's deterministic trigger table, one
  test per tool) and `backend/tests/test_routes_chat.py` (end-to-end through
  the real route: the `done` frame's `action`, the no-tool-call path
  unchanged, a failed tool call not ending the stream, chat history staying
  free of tool round-trip messages).
- Manual reasoning check, not exercised by a live provider (no network in
  this environment and none in the test suite by design): confirmed against
  LiteLLM 1.91.0's `get_supported_openai_params` that `tools`/`tool_choice`
  are supported parameters, and confirmed the streaming delta shape
  (`choices[0].delta.tool_calls[].function.{name,arguments}`,
  fragmented `arguments`) against LiteLLM's OpenAI-compatible chunk format.

## Deviations from the task brief

None from D8/ADR 0005's already-decided scope. The one judgment call made
independently, beyond what was pre-decided, is the no-progress-frames choice
for tool-invoked generation, reasoned about above, and the independent D-04
closure on `edit_master_resume` (implied by the ADR's own wording but not
spelled out as a specific implementation step).

## Cross-boundary files touched, and why

Per AGENTS.md §2, PLAN.md's task text is what authorizes touching a file
outside `domain/`/`services/` when it names the work explicitly and no other
wave-3 task owns the file:

- `api/routers/chat.py` — D-33 cannot close without changing the `done`
  event; no other wave-3 task owns this file.
- `backend/src/resumetailor/llm/{port,litellm_adapter,stub}.py` — D-33
  cannot close without tool-calling support in the LLM boundary; task 2.1
  (wave 2, `llm` role) explicitly left this unwired for this task, and no
  wave-3 task is owned by the `llm` role.
- `backend/src/resumetailor/backend_api.py` — the facade's `stream()`
  signature has to carry `tools` through to the port; not owned by any
  listed role, touched by every task that has needed to extend the port
  boundary so far (task 2.1's report notes it left this file's signature
  unchanged; this task is the first that needs to change it).
- `backend/tests/helpers/simulator.py`, `backend/tests/test_llm.py` — test
  infrastructure this task's own tests need; no wave-3 task owns
  `backend/tests/`.
- `README.md` — explicitly authorized by this task's own PLAN.md text
  ("if you finish tool calling, update those to describe the new truth
  instead").
