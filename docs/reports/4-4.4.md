## Wave 2 — spot checks

register says — this is the review's most important confirmation, not a new finding.** Read
`api/routers/master_resume.py::save_resume` directly:

```python
@router.put("/api/master-resume", response_model=MasterResume, responses=error_responses(413, 422))
```

No call to `resume_schema.validate` or `normalize_to_rendercv` anywhere on this path. Every task
that touched an adjacent file (2.5, 3.3) explicitly and correctly declined to fix this, each
saying in its own report that `master_resume.py` was not its file to touch. Nobody's report
overclaims this as closed — the register itself carries no "Fixed" annotation for D-04, which is

and P1 fixed"** before release, and D-04 is a P0 that has now survived three full waves untouched
because it sits in a file boundary nobody's task included. It is not a defect-register accuracy

**D-70 (`RuleItem` unbounded) is also still genuinely open**, confirmed by reading
`api/routers/rules.py`: `RuleItem`'s three fields are still bare `str` with no `Field(max_length=)`,
and `RulesBody.rules: list[RuleItem]` has no length cap either. Registered by task 2.2 in wave 2

in the "Next: launch Wave 4" summary — D-70 fell out of that list silently).

**D-53's SSE opacity claim across all three streaming routes — confirmed with real, non-vacuous
tests, not just reading the code.** All three: `chat.py::_error_frame`, and the equivalent
handling in `resumes.py`/`evaluate.py`, use `exc.client_message` (never `str(exc)`) and log
`exc.detail` server-side. Grepped for `xfail` across `backend/tests/`: zero results — every
`xfail(strict=True)` marker the plan's narrative describes as being removed over waves 2-2.2 is in
fact gone. Read the three live tests that replaced them
(`test_provider_exception_text_does_not_reach_the_client`,
`test_generation_stream_does_not_leak_provider_exception_text`,
`test_chat_stream_does_not_leak_provider_exception_text` in `test_security.py`): each plants a
provider exception whose message contains a fake API key and a URL, asserts the leak string is
**absent** from the response body, asserts the fixed `client_message` **is** present, asserts the
error `code` matches the raised exception's real class, and asserts the raw detail **is** present
in a log record. This is a real, specific, currently-passing regression test for exactly what
D-53 describes, on all three routes. Confirmed accurate.

**D-33's `MAX_TOOL_ITERATIONS` bound — provably bounded as claimed, with one narrow gap not
covered by the claim's own wording.** Read `domain/assistant.py::run_assistant_turn` in full. The
outer loop is `for round_index in range(MAX_TOOL_ITERATIONS + 1)` (5 iterations, 0-4); the last
iteration passes `tools=None` to `api.stream(...)`, and the very next line is
`if tools is None or not tool_calls: yield AssistantReply(...); return` — unconditional, not
contingent on trusting the provider not to return a tool call it was never offered. Traced whether
any of the four tool handlers could themselves trigger a second, nested round of tool-calling: they
cannot — `_generate_tailored_resume` calls `domain.tailoring.tailor()`, which calls
`api.complete(...)` twice with no `tools=` argument at all, so nothing inside a tool execution can
recurse back into `run_assistant_turn` or request its own tool calls. The 5-round ceiling is real
and does hold. **The one thing the claim does not cover:** the round budget bounds the number of
*rounds*, not the number of tool calls *within* one round — `for call in tool_calls:` has no length
check, so a single model response that returned, say, 500 tool calls in one round would execute
all 500 synchronously (each a real DB write or an LLM call) before the round-count check is even
reached again. Every other untrusted-input boundary in this codebase (D-47's five bounded fields,
the tool-argument Pydantic models in this same file) treats model output as exactly as trustworthy
as a POST body and no more — this one path does not. Low real-world risk (a provider has to
misbehave badly, and none of the four tools compounds cost the way, say, an unbounded LLM call
would), but it is a genuine gap in an otherwise carefully-reasoned bound. Registered as **D-78**
(P3).

## Wave 3 — spot checks (the cross-wave integration point named in the brief)

**`Chat.tsx` rendering `done.result.action` from 3.3's real backend shape — traced end to end,
correct.** `frontend/src/features/assistant/Chat.tsx` was written by task 3.2, concurrently with
task 3.3 which is what makes `action` ever non-null; 3.2's own report says it "renders whatever
`result.action` arrives without hard-coding 3.3's eventual type strings." Verified this is true
against what 3.3 actually shipped, not just what 3.2 hoped it would ship. Backend
(`domain/assistant.py`): the four tools set `AssistantAction(type=..., resume_id=...)` with
`type` values `"master_resume_updated"`, `"resume_generated"`, `"evaluated"`, `"rules_updated"`.
`api/routers/chat.py::chat_stream` turns this into
`{"type": event.action.type, "resume_id": event.action.resume_id}` on the `done` frame. Frontend:
`Chat.tsx::describeAction` splits `action.type` on `_` and title-cases it with no string matching
against any of the four literals — genuinely generic, exactly as claimed, and it produces sensible
output for all four real values (e.g. "Master resume updated"). Cache invalidation is also
correctly generic: `action.resume_id !== null` triggers a `resumes.all` invalidation regardless of
which of the two resume_id-bearing actions (`resume_generated`, `evaluated`) produced it, and
`master_resume_updated` triggers a `masterResume` invalidation unconditionally. This is a clean,
verified integration — no gap found.

**One real, narrow gap found one level deeper: an assistant-driven master-resume edit can be
silently dropped from the visible editor if the user has an unsaved local draft open at the same
time.** Followed the invalidation from `Chat.tsx` through to where it lands, in
`WorkspaceContext.tsx`. `masterYaml` is `draft ?? serverYaml`; a `useEffect` watches `serverYaml`
(the TanStack Query cache, which `Chat.tsx`'s invalidation does correctly refresh) and adopts a
server change into the visible buffer **only when `draft === null` or `draft === lastServerYaml`**
— i.e., only when there is no unsaved local edit that would be lost. This is a deliberate, well-
reasoned guard against a real prior defect (the code calls it "P1-7: props silently overwriting
state"), and as a general default it is the right call. But it creates a specific, plausible
sequence nothing currently tests or documents: a user is mid-edit in the master-resume editor
(dirty, unsaved), asks the assistant via chat to "update my summary," the assistant's
`edit_master_resume` tool call succeeds server-side and the chat UI shows "Master resume updated,"
but the editor pane the user is looking at does not change — it still shows their own stale,
unsaved draft, with no indication that the server's copy has moved out from under it. If that user
then saves their draft, they silently overwrite the change they just asked the assistant to make,
with no conflict warning of any kind. Registered as **D-79** (P3 — plausible, not exercised by any
test, but requires a specific timing coincidence a single user has to create themselves).
